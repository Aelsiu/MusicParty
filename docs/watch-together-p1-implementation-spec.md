# 一起看视频 P1 实施规格

版本：v1；日期：2026-10-05。用户已确认核心产品规则及等待参数。本规格作为新会话实施依据；其余默认工程规则在下文给出，不表示功能已实现或验收通过。

## 1. 本轮范围与已确认规则

P1 在现有 P0 协调器、双引擎和双队列上增加 DASH、多画质、提前续期、分 P、倍速同步及全员缓冲等待。

用户已明确：

- **画质由各端独立选择**，设置入口位于原设置界面的“歌词提前显示”下方。
- **切 P 后从头起播**，新 P 的起始媒体时间为 0。
- **全员缓冲等待纳入本轮**，不再留到 P3。
- **任一观看端持续真实缓冲 2 秒触发等待，单端最多阻塞 15 秒**；超时使用已有顶部提示框显示阻塞用户名。

继续保持音乐模式行为、房间权限、双模式现场隔离和客户端直连视频媒体。Cookie 只用于服务端解析，不发送给成员；媒体不经本应用代理、缓存或 FFmpeg。会员、付费、番剧、区域限制内容，以及画中画、原生媒体全屏、锁屏控制和弹幕，不因上述三项确认而自动扩大支持范围。

## 2. 本端画质设置

### 2.1 入口和展示

在 `SettingsModal.vue` 的“其他设置”卡片内，紧接现有“歌词提前显示”块，增加同级“视频画质”设置项。保留原布局与主题样式，不把它放进房间管理台或底部房间控制条。

默认“自动”，并按当前可信来源和设备能力提供实际可用的画质档。音乐模式下可保存视频画质偏好；没有视频或当前只能使用 MP4 时说明当前可用情况，不展示虚假的高画质选项。短提示说明“仅影响本端观看”。

偏好与实际画质分开：例如本端偏好 1080p，当前视频 / Cookie / 设备仅能使用 720p，应展示实际档位并在本端回退，不覆盖用户保存的长期偏好。实际是否支持某个档位必须以解析响应和设备验证为准。

### 2.2 状态边界

- 画质偏好保存在本浏览器的 UI store / localStorage，键名 `mp_video_quality_preference`，不进入房间共享设置或 SQLite。
- 保存带版本的“自动 / 手动 + 稳定画质标识”偏好；不保存实际 codec、签名 URL、播放器代次或源版本。损坏数据、无效值及存储不可用时回退自动。
- 本端画质选择不改变房间播放进度、倍速、播放意图、播放实例和其他端画质，不发送全房间画质控制。
- 服务端提供可信的可用来源集合；客户端在其中选择兼容轨道。不能接受成员提供的任意 CDN URL。
- 换画质前后使用同一房间时间线及倍速。完成后按当前房间状态恢复播放或暂停；若正在全员等待，则继续预缓冲并报告就绪。
- 增加本端来源代次，隔离旧画质的 manifest、segment、play Promise 和错误回调；单纯替换同值房间心跳不得重新创建播放器。
- 本端画质切换引发的真实缓冲遵守 §6 全员等待策略；画质选择本身不直接广播全员暂停。
- ArtPlayer 自带播放、seek、倍速及快捷键必须接入房间控制与权限；程序同步事件不反向发送房间指令。不能保留另一套可绕过权限的原生控制。

## 3. 分 P 与切换

- 服务端读取并校验全部 P 的可信元数据，采用 `BV...:pN` 标识选定 P；cid、标题和时长来自可信响应，不由客户端决定。
- 输入链接 `?p=N`、选 P 入队和当前视频切 P 必须明确区分；每个 P 独立检查视频时长和入队限制。
- 当前视频切 P 创建新的播放实例，媒体时间重置为 **0**，清理上一 P 的源、等待状态和过期就绪报告。旧异步结果不得提交到新 P。
- 同一 P 内换画质或续期继续保留时间；不能把旧 P 的时间数值套用到新 P。
- 新 P 沿用切换前的播放 / 暂停意图，解析和预缓冲阶段由新实例状态协调。当前视频切 P 默认仅允许 Owner / Root，并尊重跳过锁；锁定时先按现有权限解除锁。普通成员选 P 入队沿用现有入队权限。
- 自然结束继续使用已有队列和播放模式，不自动播放未入队的下一 P；需要连续观看的 P 应明确入队。
- 切 P 不隐式批量入队所有分 P，不绕过现有队列、配额、锁或投票规则。

## 4. DASH 与提前续期

来源契约需覆盖音频轨、视频轨、codec、画质标识、可信时长、初始化 / 索引范围、主备 CDN 地址以及可观察的期限。B站 DASH 响应到可播放 MPD / manifest 的适配、CDN CORS、Range 和编码支持需要独立验证；不能以安装 ArtPlayer / dash.js 代替双轨播放证据。基础接入参考 [dash.js Setup](https://dashif.org/dash.js/pages/quickstart/setup.html) 及 [ArtPlayer customType](https://github.artplayer.org/document/en/start/option.html#customtype)。

客户端依据能力选择 DASH；不具备所需能力或来源不可用时按明确规则回退 MP4，继续服从同一房间时间线。iOS 按实际浏览器、库版本和设备能力验证，不按系统版本直接保证支持。

提前续期复用当前 mailbox、Cookie 版本隔离、刷新合并、源版本和退避基础，但必须与首次解析、恢复失败源区分：

- 只根据可信期限和有界软新鲜期制定续期计划，不假定地址固定两小时失效。
- 考虑音视频两轨及提供给不同端的可用档位；不得只更新视频轨而继续使用过期音轨。
- 后台解析期间继续使用仍可播放的旧源，不能仅因续期开始冻结房间时间或拒绝正常控制。
- 提交新源时读取当前播放意图和当前锚点，保持同一 playbackId，推进 sourceRevision；不得使用任务开始时的旧进度或旧暂停状态覆盖后续 seek / pause。
- 自然结束、next、切 P、切模式、Cookie 更新和关闭均须使不匹配的结果失效。
- 解析失败不自动 next；保留可用旧源及当前媒体，按退避重试。旧源确实失效后由真实客户端缓冲和最终等待策略决定是否全房间等待。

默认仅为有人且处于激活 VIDEO 的当前媒体提前续期；暂停时可在临近恢复所需有效期时续期，不恢复播放意图；非激活或空房不定时解析，恢复时检查新鲜度。优先沿用现有 5–60 秒有界退避和 singleflight。

可信期限的触发窗口、未知期限的软新鲜期以及最低请求间隔由真实来源验证确定，并写回验证记录；不需为普通工程参数逐项再次确认，但不得改动用户确认的 2 秒 / 15 秒规则。临时源不持久化，日志不记录 Cookie 或完整签名 URL；运行时解析和向已授权观看端下发临时地址是直连播放的必要行为。房间 Cookie 配置继续使用已有本地凭据管理机制。

## 5. 倍速与播放时钟

倍速是房间级 VIDEO 状态，与本端画质区分。修改速率时服务端先按旧速率计算并冻结当前进度，再建立新锚点；所有前端的快照延迟补偿、进度推进和 video.playbackRate 使用同一服务端速率。

默认档位为 0.5、0.75、1、1.25、1.5、1.75、2，仅 Owner / Root 可修改。倍速属于 VIDEO 房间设置：换画质、换 P、换片和切模式保留；随 VIDEO 设置持久化，旧快照缺失时默认 1。Music 时钟不受 VIDEO 倍速影响；缓冲等待和手动暂停期间 elapsed 不推进。

## 6. 全员缓冲等待

### 6.1 已确定的不变量

全员等待必须冻结服务端房间进度，并由服务端统一发布恢复状态。不能只暂停几个客户端而让房间时钟继续前进。

**手动播放意图与缓冲等待是两种独立状态**：

- 手动暂停在缓冲恢复后仍保持暂停，自动恢复不能覆盖它。
- 等待期间本端暂停展示 / 播放，但仍允许音视频预缓冲；不能因为调用 video.pause() 就把缺数据的端误判为就绪。
- 本端就绪依据冻结位置的可播放数据、音视频轨就绪和播放器错误状态判断，不单靠某个 canplay 回调，也不靠持续增长的媒体时间。
- 正常 stalled 下载事件、自动播放被拒或用户尚未点击本地解锁，不能直接作为真实缓冲阻塞所有人。
- 等待状态下 onReady、playing 回调和 200ms 同步任务不能自行 play，也不能反向发送房间播放指令。
- 等待 / 就绪报告绑定当前连接、房间、epoch、modeEpoch、playbackId、sourceRevision 及本端来源代次，带单调序号；旧连接、旧 P、旧源和迟到回调均不能影响当前等待。
- 每次等待有独立 waitId 和 waitRevision，并发布冻结位置。解除等待需要匹配 waitId + waitRevision + sourceRevision，针对当前冻结位置重新确认 READY；屏障之前缓存的 READY 不能解除新一轮等待。
- 等待期间获授权的 seek 修改冻结位置，倍速改变就绪水位；两者均推进 waitRevision、撤销旧 READY，而不重置截止。手动暂停取消当前屏障和自动续播，之后的 READY / 续期不得恢复播放，也不再产生已取消屏障的超时通知。
- 就绪必须验证等待锚点处已定位、未 seeking、音视频两轨均覆盖恢复水位且可解码。水位随房间倍速换算，并处理接近片尾的剩余时长，不能要求片尾不存在的额外缓冲。
- 断线、切模式、切 P、next、房间关闭及等待超时有明确清理；全员等待不是无限阻塞房间的开关。

### 6.2 已确认等待策略与实现规则

用户已接受任一观看端触发、2 秒阈值、15 秒上限和超时实名提示。按以下规则实施：

1. 任一正在观看的端持续真实缓冲 **2 秒**后触发全房间等待。
2. 所有参与判定的端对冻结进度就绪后，若用户播放意图仍为播放，统一恢复。
3. **15 秒从服务端创建等待屏障并冻结锚点时起算**，不包含触发前房间仍在播放的 2 秒检测期。使用服务端单调时钟计时，截止时移除仍未就绪的阻塞端；所有剩余端就绪且播放意图未暂停时恢复。
4. 超时端继续本地加载，恢复后对齐并跟随观看；同一播放实例内不自动恢复其阻塞资格，避免弱网反复触发全员停播。新播放实例才清理该排除记录，手动暂停 / 恢复、新 waitId、换画质、续期和本端来源代次变化均不能清理。

持续缓冲时长由服务端首次接受有效 BUFFERING 报告起计算，不接受客户端提交的任意起始时间。重复报告不重置检测起点；2 秒之前有效恢复为 READY 时撤销触发计时。

观看资格使用有效连接、已同步、前台及已允许本地播放作为基础；游客与命名成员都可提交观看状态，但不因报告取得房间控制权限。首次加入尚未就绪、后台、自动播放被拒及不可恢复编码错误的端不阻塞房间；已合格端正常换源不能通过重建元素绕过缓冲判定。等待产生的程序暂停不让其失去资格。进入等待时固定参与集合，新加入端不延长当前屏障；断线、后台退出和状态租约过期及时退出，退出本身不弹“超时”。

状态报告正常每秒一次，租约默认 6 秒；等待期间继续心跳，不依赖媒体是否产生播放事件。资格与排除记录由服务端关联已验证观看身份；同一观看端重连不能清除当前 playbackId 的超时排除记录，也不能信任任意客户端标识来重置预算。连接世代与本端来源代次分开；各端代次数值不跨端比较。

新增独立的 `/app/video/watch/status` 观察通道，报告 PREPARING / READY / BUFFERING / BLOCKED / ERROR / INACTIVE。身份取自服务端连接，校验房间和实例上下文，限频并采用有界短租约；报告不能直接设置房间播放意图或锚点，不能套用普通媒体控制的“必须命名”授权而禁止游客提交本端能力状态。

快照需区分 playIntent 与有效暂停状态：进入等待冻结锚点而保留 PLAYING 意图；手动暂停切换意图为 PAUSED。toggle-pause 按意图操作，不能把“正在等缓冲”误判为用户已经手动暂停。等待信息至少包含 waitId、冻结进度、人数和截止时间，不向公共快照暴露原始会话凭据。

同一轮真实缓冲的固定 15 秒截止，不能因重复报告、换画质、元素重建、源版本更新或人为重建 waitId 而后移。非超时端全部 READY、屏障正常解除且房间已恢复播放后，之后真正新发生的缓冲可以建立新一轮等待；这不是每个 playbackId 累计 15 秒的预算。但已经发生的超时排除记录在同一 playbackId 内始终保留，实际恢复或新 waitId 都不能撤销它。

手动暂停取消当前等待轮次，不再产生该轮超时通知；后续显式播放可以按当前真实缓冲建立新轮次，但已发生的同实例超时排除仍保留。

提前续期成功推进 sourceRevision 时，已有等待冻结点和截止时间保持不变，各端针对新源重新确认 READY。切 P / next 清理旧屏障；切模式、空房暂停和关闭还要取消自动续播。等待、租约和就绪集合均为运行期状态，不持久化。

### 6.3 超时顶部提示

- 服务端实际达到阻塞截止时，发布房间级 `VIDEO_WAIT_TIMEOUT` / WARN 事件，携带 eventId、waitId、播放上下文和阻塞端显示名。断线、租约退出、取消屏障和旧实例回调不冒充超时。
- 复用现有 `/topic/player/events` → `socketHandler` → `useToast` → 顶部 `ToastNotification`，不新建提示组件。标题为“等待缓冲超时”，文案为“「张三」缓冲等待超过 15 秒，已暂时退出等待判定”。其他端仍未就绪时不宣称全员已恢复。
- 名称取自服务端成员记录，保留事件内显示名供成员离线后展示；游客显示“游客”，必要时用非敏感的公开观看端编号区分，缺失时显示“一位观看成员”。不展示 token 或原始 sessionId。
- 同一端同一屏障只通知一次；客户端按 eventId 有界去重，不从每次心跳重复产生通知。消息匹配当前播放上下文即可，不要求等待此时仍 active，因为超时事件可能在解除状态之后送达。
- 顶部提示沿用现有视觉与位置。此类消息允许换行，限制视口宽度，保证用户名不会被现有 truncate 截掉。

## 7. 实施与验收顺序

1. 真实 DASH 双轨与 MP4 回退验证：画面、连续声音、时长、Range / seek、CORS、codec 及来源期限。
2. 来源、倍速和等待状态采用 protocolVersion=3，保留单协调器、单激活快照和上下文屏障；同步更新 STOMP / HTTP / 前端屏障，protocol 2 客户端明确提示升级，获得新媒体源前拒绝连接。MUSIC 产品行为保持一致。
3. 接入本端画质设置、换轨与提前续期，再完成分 P、倍速和全员等待。
4. 回归音乐模式和 P0 生命周期；保持已修复的重复 seek、同源心跳 reload、stalled 假缓冲问题不复发。

新增验收至少覆盖：

- 两个端选择不同画质，另一端的选择、进度和倍速不受直接修改；设置项位于歌词提前显示下方。
- 切 P 后两端都从 0 起播，新旧 P 的音视频轨、源报告和等待状态不串用。
- 单端真实缓冲触发等待，房间锚点冻结；恢复后统一继续。
- 等待期间手动暂停，恢复缓冲后仍不播放；等待期间换源、seek、切 P、切模式、断线和超时不会卡死或错误恢复。
- 本地解锁、正常 stalled、后台端和过期报告按资格规则处理；重复报告不能无限延长等待。
- 1.999 秒不触发、到 2 秒触发；等待 14.999 秒不超时、到 15 秒移出未就绪端并弹对应用户名。取消、断线及租约退出不弹超时，重复公共 / 私人事件只弹一次。
- 多阻塞端分别展示身份；已超时端的恢复、切画质、同实例续期及重连不反复阻塞，提示在窄屏仍能完整辨认名字。
- 双轨持续有声、倍速一致、换画质 / 续期保持位置；报告要求的 1080p 连续 2.5 小时用例需测试环境有足够时长上限，并区分自然长时验证与受控失效。

真实 HTTPS、不同网络和手机测试条件继续按用户此前安排后补，桌面本地验证不能计作这些验收通过。上述测试在功能实施后执行，本规格不是测试结果。
